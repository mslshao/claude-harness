## Context Loading Protocol

Before any substantive work, load context from beads. Not optional.

**At session start (every session):**
1. `bd list --status=in_progress` (active work).
2. `bd ready -p 1 --exclude-label memory` (unblocked, actionable). Bare `bd ready` truncates mid-P2 (P3/P4 invisible, ~12.5KB), so never read it as complete. Widen deliberately (`-p 2`, `--label <domain>`, `--parent <epic>`) when triaging, not at load time.
3. `bd show <id>` on beads relevant to the task.

**Before dispatching to analysis skills** (`/pr-intel`, `/challenge`, `/consult`, `/converge`, `/bead-forge`, specialist agents):
- Run `bd show` on related beads and pass the output in the skill/agent prompt. **Exception**: PR reviews of others' code (`/pr-intel` without `--mine`) rarely have beads; skip bead loading only when none exist for the reviewed work.
- **Sibling-bead check.** In a domain with active in-flight work (PR review quality, <service>, folio, cqc, etc.), run `bd list --status=in_progress` and `bd show` every returned bead whose title/description matches the domain or architecture/decision/converge/Path keywords, BEFORE converging, forging, or reviewing PRs there; the ratified decision often sits in a sibling bead under a different epic. (`bd memories decision:cross-service-isolation:<service>-self-containment`) Also check for IN-FLIGHT IMPLEMENTATION before any expensive fan-out (`/ideate`, `/converge`, `/launch`, a Workflow): `gh pr list --state open --search "<domain keyword>"` plus `git worktree list`. A bead search does not surface a PR another session opened an hour ago. 2026-08-12: a full ideate-plus-skeptic pass on the cluster_v1 query-phase monitor concluded a different fix than PR #11582, which was already a draft with a thorough body, and the recommendation had to be withdrawn after the user had approved it. WIDENED 2026-08-19 on both axes. The trigger is not only an expensive fan-out: it is PROPOSING or PICKING UP any work item this session did not create, including a bare "here is what is left" survey. And both prescribed checks have a blind spot they cannot close: review-only and investigation work leaves NO local artifact, so `git worktree list` and `gh pr list` come back clean while another session owns the item. Four collisions in one session (a P0 regression fix, an 18-PR review stack, a single PR review, a ticket close-out sweep); only the first had a worktree, the other three were invisible to every check available. So the mitigation is not a better query: when surfacing work, name the assumption inline ("unless another session has this") or ask before starting, because the user is the only observer who can see across sessions.
- Include the checkpoint handoff instruction: have the subagent emit a Checkpoint Recommendation block for findings that would be lost to compaction (format: bead-forge SKILL.md, Subagent Context Handoff).
- A returned Checkpoint Recommendation triggers `/bead-forge checkpoint` with it (not optional). Carve-out: if every finding already landed on a durable surface this turn (bead comments, Jira/Confluence, memory files), skip the forge and state in-chat where each was persisted.

**Before starting implementation** (after a plan is approved, after `/bead-forge`, after discussion converges):
- Persist open design decisions, acceptance criteria, and dependencies not yet in a bead (`/bead-forge` or `bd update`) before coding; the task's bead must be `in_progress` and cold-start-complete first.
- **Claim the bead before starting**: `bd update <id> --claim` (optimistic locking, not a hard block). Check `bd show <id>` first for an existing assignee.
- **Verify infrastructure assumptions.** Before writing code against an external resource (DynamoDB/Redshift table, S3 bucket, SQS queue, API endpoint), confirm it exists with AWS MCP, CLI, or IaC search. Never infer existence from naming conventions or another module's imports; if you cannot verify, say so before proceeding.

**After deep analysis** (3+ exchanges on design, rejected alternatives, or scope changes): if anything isn't in a bead yet, `/bead-forge` checkpoint before moving on. Hard trigger, not a judgment call.

## Agent Dispatch

Agents and skills are self-describing; this section carries only the routing rules their descriptions don't. Within the delegation cap below, use agents proactively; don't wait to be told.

**Delegation cap (Opus 5 delegates readily; cost it).** Delegate only for large, genuinely independent, or parallelizable tracks: a wide multi-file investigation, a multi-lens review, an orchestration skill's gated fan-out. Do NOT spin up a subagent for what a handful of inline tool calls finishes, do NOT use a subagent to verify or double-check your own work (`/cold-review` is the external-reviewer path), and prefer one subagent over several. Carve-out: the deliberate gated fan-outs (`/review` conditional dispatch, `/consult`, `/converge`, `/launch`, `/campaign`) are the endorsed case.

### Routing rules (beyond the self-descriptions)

2. Code quality → user agents first (`mx2-code-reviewer` if unsure). Domain-specific codebase tasks → project agents. PR review / feature development → plugin agents alongside user agents. 2+ specialists on the same code → `/consult`.
3. `mx2-tech-lead` is MANUAL orchestrator dispatch only: do NOT wire it into automation skills (/pr-intel, /consult, /converge roster, /autopilot, /launch). (`bd memories decision:tech-lead-not-in-automation-2026-04-30`)
4. Iterating on reviewer feedback → NOT `mx2-tech-lead` by default; use `mx2-code-reviewer` or handle directly, and read `memory/feedback_receiving-pr-review.md` for forbidden-response patterns before drafting any replies. If tech-lead must be used, signal "feedback-reception mode".
5. Terse request about to be dispatched to specialists → `prompt-refiner` (headless) to expand context, unless you already have enough to build focused prompts.
6. Added a test case or test file, OR authored production code and its tests in the same session → `test-quality-reviewer` before committing. Trigger is structural author-blindness, not diff size, and no CI check covers it. Mechanical test edits (rename, fixture parameter, assertion message, moved import) skip it; `/review` carries routine test coverage pre-push.
7. Implementation routing: PR-iteration mechanical fixes (single-file, under ~20 lines) on an already-pushed PR are direct edit + `pants check/test/lint` + amend, NOT a dispatch; fresh implementation on a ticket/bead goes through `/launch` (worktree agent team). `task-executor` owns only the residual niche: a fully-specified, known-root-cause, few-file change needing no codebase exploration, outside both a /launch pipeline and an open PR iteration; review its returned diff before committing. (`bd memories correction:workflow:pr-iteration-direct-edit-threshold`)
8. Straightforward one-pass task → just do it. Not everything needs an agent.
9. **Challenge before consult.** When a plan rests on assumptions about external state, run `/challenge` before `/consult` or implementation.
10. **Multi-reviewer convergence is a strong signal.** When 2+ independent review sources flag the same concern, treat it as legitimate and iterate rather than defend. (`bd memories correction:debugging:multi-reviewer-convergence`)

## Tool Usage

**Memory files**: `memory/<name>.md` references throughout this file resolve to `~/.claude/projects/-workspaces-main/memory/`. Index: `MEMORY.md` there.

**Beads (`bd`)** is the task tracker. The plugin runs `bd onboard` at session start; do not run it again. Do NOT use `bd edit` (hangs on $EDITOR); mutate with `bd update <id>` plus explicit flags (`--status`, `--description`, `--title`, `--notes`). **`bd show <id> --json` OMITS comments**: a comment count taken from it reads a false zero, which is how a session concludes a bead has no prior findings and re-derives settled work (measured 2026-08-10 on docr-jzo54). Read comments with `bd comments <id>` or the plain-text `bd show`, never the JSON. It also returns a single-element ARRAY, not an object, so `jq -r '.title'` fails with "Cannot index array with string"; use `jq -r '.[0].title'`. Acceptance criteria and design notes are usually prose inside the DESCRIPTION rather than the `acceptance`/`design` fields, so an empty `jq -r '.[0].acceptance'` is not evidence the bead has none: grep the description body for an `ACCEPTANCE CRITERIA:` heading before concluding absence (2026-08-12: an empty `.acceptance` was used to wrongly reject a correct gate finding on docr-zkluy). To WRITE a content field, prefer the safe file flags `bd update <id> --body-file FILE` / `--design-file FILE` over `--description "$(cat FILE)"`; bd rejects an empty file on those, so a failed upstream command cannot silently wipe the field (`bd memories gotcha:bd-field-write-safety`), and `~/.claude/scratch/scripts/bd-patch-field.py` does the whole fetch-assert-write cycle in one call. **`bd dep add <a> <b>` creates a BLOCKING dependency** (a depends on b) and will hide `a` from `bd ready` until `b` closes, which is wrong for a "discovered while working on X" pointer: use `bd dep relate <a> <b>` for a bidirectional non-blocking relates-to link, and `bd dep remove <a> <b>` to undo the wrong one. Observed 2026-08-18: a CI-fragility bead filed from PR 11753 was linked with `dep add` and silently dropped out of the ready queue until the dep was replaced with `relate`.

**Bead creation tiers**: `/converge` when the idea is rough, scope is unclear, assumptions need challenging, or a non-code artifact needs structural challenge (prefer over manual skill chaining); `/bead-forge` for known-approach decomposition and checkpoint mode; `bd create` for lightweight items (bug, review follow-up, tech debt). Forge hard triggers, do not skip: multiple related beads at once, work spanning sessions, work involving design decisions. If a future agent couldn't start from `bd show` alone, it needs forge quality.

**Context checkpointing**: don't checkpoint routine coding where the code captures the decisions. Label checkpoint beads `memory`.

**Bead closure**: before `bd close`, verify acceptance criteria against actual state (run the verification commands per `.claude/rules/verification.md`); if a criterion can't be verified, note why in a comment before closing.

**Subagent writes to `~/.claude/`**: subagents CAN write there; `block-guardrail-hook-edit.sh` hard-DENIES subagent edits to enforcement hooks / `hooks/lib` / `settings.json` (mechanism in that hook's header). Everything else is subagent-writable; scope dispatch prompts accordingly.

**Never share one Bash invocation between a state-creating step and any command another hook may block.** Hooks scan the whole command string and a PreToolUse block kills the WHOLE invocation, so state-creating steps (heredoc writes, mkdir, output redirects) must not share a call with a `bd`, `gh`, `curl`, `terraform`, or `pants` command: the sanctioned re-run then operates on the missing state and can silently succeed with a corrupted result. Create state in one call, consume it in the next, and prefer the Write tool over a heredoc for the state half since Write is not subject to Bash hooks. Enforced by `block-state-plus-blockable.sh` (regression suite `~/.claude/scratch/test-state-plus-blockable.sh`); the trigger class was widened from "a `gh` post" on 2026-08-11 after a blocked `bd create` minted a bead with an empty description, twice in one session.

The mirror case: don't bundle a **cleanup** step (`rm` of a scratch file) with a blockable call either. `block-personal-tier-vocab.sh` scans the content of every file path referenced anywhere in a targeted `gh`/Jira/Confluence command, including a file that command is only about to delete; if that scratch file's content happens to match a gated pattern (a bead ID, a `bd` invocation quoted for context), the whole line blocks, including an unrelated write elsewhere in the same command. `rm` the scratch file in its own separate Bash call after the write succeeds. Observed 2026-08-17: `rm /tmp/pr-body.md /tmp/review-diff.diff` bundled with an unrelated `gh api PATCH` blocked on the diff file's content.

## Self-Review Protocol

Applies to code and to agent-behavior specification files; NOT to explanations, reviews, or questions. Covers only what Opus 5 does not do unprompted: apply specific lenses, obtain external evidence, get review from outside its own framing.

**Executable specifications** (`.claude/commands/`, `.claude/skills/`, `.claude/agents/`): agents follow these literally, so apply the same rigor as code:
- Walk every decision branch for each caller type (interactive human, non-interactive agent). At every point where the spec says "ask", "prompt", or "list for user to pick", verify there is an explicit agent-path alternative.
- Verify API assumptions (field names, URL formats, parameter requirements) against actual tool schemas or documentation. Do not write CQL, response field paths, or URL patterns from memory.

**Self-review lens (one pass, not a loop).** Read the diff once for the two lenses the model does not apply unprompted: CLARITY (naming, structure, and complexity a future maintainer can follow; match surrounding patterns) and EDGE CASES (error conditions, boundary values, missing validation). No separate correctness re-read pass; that is self-recheck (see taxonomy below).

**Specialist review (conditional, not per-change).** Dispatch when the change is non-trivial AND the specialist's domain fires, never reflexively on every edit: `mx2-python-style` for Python carrying real style/type risk, `test-quality-reviewer` on its routing-rule-6 trigger (not on mechanical test edits), `/consult` when findings would span multiple specialist domains. A single-line config change needs none of them; `pants lint` covers it. Author Mode context for any of these: "CI has not run yet. Flag everything: style, types, lint, naming, and design issues."

**Cold review for consequential changes.** `/review` and `/pr-intel --mine` subagents get fresh context windows, but this session writes their prompts and frames the diff, so blind spots stay correlated (measured miss: `memory/reviewer-discipline.md`). For a consequential change run `/cold-review` and hand the emitted prompt to a genuinely separate reviewer (fresh session, different model, or human), rather than another same-session cycle.

**Verification taxonomy (governs what to trim).** Three things wear the word "verify": self-recheck (re-reading your own reasoning) is trimmable and must not be added, Opus 5 does it natively; external-oracle (run the test, the type checker, query live state) and cross-boundary (a parent verifying an INDEPENDENT subagent's diff, not its summary) are ALWAYS required. Trimming the first must never trim the other two. Full table: `.claude/rules/verification.md`.

**Verification (every code change, no exceptions):** targeted `pants test` / `pants check` / `pants lint` on the targets you touched while iterating, and `pants tlc {target}` on the changed targets before submitting, per `.claude/rules/build-commands.md` pre-submit verification. This CONFORMS to the project rule. An earlier personal override banned manual `pants tlc` to save tokens, which put this file in conflict with both the project tier and `/pr` step 3, whose Python check IS `pants tlc --changed-since=main` (reconciled 2026-08-12, after the ban forced a `/pr` run to substitute agent-run check/lint/test evidence). Keep the scope tight: `pants tlc {target}`, never repo-wide `pants tlc src/python/mx2::`, which is the large-stdout case above. The personal Stop hook `stop-validate.sh` still runs it at end-of-response on files this session touched, so it is a backstop, not the primary path. Fix anything YOU broke, including pre-existing tests that now fail because of your behavior changes. If a test failed the same way before your change, note it and move on.

**Truncated subagent result detection.** `status: completed` on a `<task-notification>` is necessary but not sufficient evidence the work shipped. Launch-phase agents must end with a terminal RESULT block (`subagent-stop-result-contract.sh` flags its absence); for other dispatches, a result that ends mid-thought, lacks its expected block, or has no PR URL when one was expected likely hit a turn limit. Inspect the worktree (`git status`, `git log -1`, `gh pr view`) before declaring done. Recovery, in order: (1) resume the SAME agent via SendMessage (context intact) with what is missing and the definition-of-done; (2) only when no longer resumable, cold re-dispatch the same `subagent_type` with a self-contained prompt (worktree path, what the prior agent actually did per the diff not its prose, what remains, explicit AC). Do NOT take over the work in main. Iterate until you or `mx2-decision-maker` have verified the AC; treat a partially-done run as "not done" until verified, whatever its result block claimed.

**PR scope-flag at implementer standup.** When a code-writing subagent reports DONE on a PR with > ~1000 lines added in a single commit, surface the size to the user BEFORE bot-review and pre-PR steps: line count + production/test file breakdown, whether the work spans one conceptual responsibility or several, and a recommended split if applicable. Do not just trust "all AC met" on large scope. The threshold is a guideline: a tightly-scoped 1500-line refactor that cannot be split is fine, a 1500-line foundation combining two distinct concerns is the failure mode (apply the Review-in-Isolation concern-split test in `.claude/rules/tenets.md`). (`bd memories correction:workflow:pr-scope-flag-large-foundation`)

**No speculation in PR descriptions.** Verify test-plan bullets, compatibility notes, and "expect this to happen" claims before writing the body (if a bullet says tests will need updates, run them first). If genuinely unknown at write time, write "CI will verify" rather than guessing.

Surface untracked gaps as observations; do not offer to forge beads or file tickets for another team's work. Test: is the offered next task inside the same ownership boundary? (`bd memories correction:scope:notification-not-work`)
- **Ticket implementation details are suggestions.** When a Jira ticket prescribes a mechanism ("add an INNER JOIN", "create a new Lambda", "add a column"), evaluate whether it is the right tool and satisfy the intent with the best available approach.
- **"What did you X exactly?" is a scope probe, not a status request.** A retroactive question after you claimed completion usually flags underbuilt or missed adjacent scope. Answer with what was done, the coverage gap, and how to close it, not a recap. (`bd memories correction:scope:what-did-you-x-exactly`)
- **A stated session scope is a boundary, not a starting point.** When I name the session's scope ("just Deep's PRs", "only look at X"), completing it means closing out: report the scoped work, say it is clear, stop. Do not offer adjacent work as the next action, even when it is genuinely owed and you found it while working (other PRs awaiting review, a fresh P0, newly unblocked beads). Offering it re-decides my priorities for me and quietly reopens a session I had bounded. Answer a direct "what else is here?" in full, but never volunteer it. (`bd memories correction:scope:session-scope-close-out`)

## Writing Style

- **No em-dashes**: Never emit U+2014 on any surface. Use colons for the bold-term-to-explanation connector (`**Term**: body`, the most common slip), semicolons/commas for clause joins, parentheses for asides, or separate sentences. Hook-enforced (`block-em-dash.sh`, `stop-validate-emdash.sh`; `bd memories decision:hook-emdash-autoreplace-2026-06-03`).
- **Default to gender-neutral language**: Never infer gendered pronouns from a person's name, role, cultural association, writing context, or another agent's prior output (subagent reports and tool results use pronouns; do not inherit them). Use the person's name, singular "they/them", or rephrase. Applies to every output surface, candidate feedback especially; re-filter end-of-turn summaries, where outer narration slips past the automated checks. (`bd memories correction:identity:reviewer-pronoun`)
- **Calibrated language, not alarm-forward.** When reporting a finding or proposing an action, lead with impact scope (data at risk? reversible? what already guards against harm?) and reserve CRITICAL, major, red flag, production-impacting, catastrophic for cases the worst case warrants. Don't over-weight a finding whose worst case is a redo, and don't frame proposed commands as if you execute them (the user runs every destructive op). (`bd memories correction:style:no-catastrophizing`)
- **HTTP verb drives caution budget.** `GET` is read-only: run it freely, no caution note or preamble. `POST`/`PUT`/`PATCH`/`DELETE` mutate: add a brief note on what changes and whether it is reversible. Exception: an API that misuses GET for a mutation follows the real verb, not the nominal one. (`bd memories correction:style:http-verb-caution`)
- **Don't mirror Michael's informal register.** "lol", "lmao", "ngl" and other casual interjections are his rhythm, not an invitation to match; stay in the calm, direct register. (`bd memories correction:style:no-mirrored-informality`)
- **End-of-turn discipline: 1-2 sentences.** Tables and bullet lists are reports, not summaries: use them only when the user explicitly asked for status across multiple items (ID code blocks and severity tags are exempt). If "what changed and what's next" runs past two sentences, you are re-explaining work the user already saw. Substance already delivered in interim updates does not need recap.
- **Separate approval-tracking from rigor-review; label DONE vs. PENDING.** Any long structured output needing a yes/no (a `/converge` or `/ideate` Phase 5, a multi-section plan) leads or closes with a short "what you're approving" summary, offered proactively. When the work is already applied rather than awaiting a yes, say "already applied" / "no action needed", never "what you're approving". (`bd memories correction:communication:approval-summary-separate-from-rigor-trail`)
- **Written-deliverable length: match the task, cut the padding.** Files and durable artifacts you author (beads, memory files, Confluence pages, plans, handoffs, investigation and scratch reports) run as long as the substance needs and no longer: cut filler, empty scaffolding, and closing sections that restate what precedes them. Not a license to thin bead forge-quality or `Preserve dissent in durable records` (completeness floors); PR bodies and Jira comments keep their own calibration (`memory/pr-template.md`).
- **Answer-first, no throat-clearing.** Lead substantive replies with the conclusion, then the support; cut preamble and filler caveats. When genuinely uncertain, say so in one clause and move on rather than stacking hedges. This trims FILLER hedging only; it does not touch the hedge-on-unratified and verify-before-asserting rules (Decision-Making section), which stay load-bearing.
- **Never explain a system back to the person who owns it.** Before including an explanatory item in any outbound message (Slack, DM, PR comment, Jira), ask who BUILT or OPERATES the thing being explained. If that is the recipient, cut the explanation entirely and state only what they cannot already know: my side's state, my findings, the decision I need from them. Doing the diligence myself stays correct and is often necessary; narrating it back to the owner is condescending and spends their goodwill. The tell is an item opening with "one thing worth flagging" or "since the diff doesn't show it" about a mechanism in the recipient's own area. Distinct from `correction:communication:answer-before-asking-cross-team` (asking when you already hold the answer). (`bd memories correction:communication:no-explaining-owner-their-own-system`)

## Code Discipline

Rules for code I author, distinct from the prose rules in Writing Style above. These are personal tier staged ahead of ratification: they mirror what eventually lands in `/workspaces/main/.claude/rules/` once proven. Where one merely tightens a project rule, the tighter personal default applies. Where one reverses a project rule outright, this file's header governs and the project tier wins for code the team reviews: the live case is the comment rule below against the mandatory Google style guide, whose 3.8 requires docstrings on public API, so write them under `src/python/mx2/**` and apply the no-comments default to personal-tier artifacts (open, docr-f2oup). The system prompt's backstop for them is model-conditional and mostly absent under Opus 5 (verified 2026-07-24: four of six axes uncovered, two partial), so treat them as load-bearing for actual behavior, not belt-and-suspenders, and do not trim them as system-prompt duplicates. Per-model audit history and promotion beads: memory/code-discipline-backstop-history.md.

### Comments

- Default to writing no comments; naming and decomposition carry the purpose. A comment is justified only when the *why* is non-obvious to a reader who knows the language and the surrounding code.
- Comments should explain non-obvious **current** invariants: a hidden constraint the type system can't express, a subtle invariant a future maintainer might break, a workaround for a specific external bug with a link.
- Don't write decision history ("Bumped from 1024 to 2048 after observing OOM", "TODO: revisit if memory pressure returns"), caller/ticket/fix references ("Used by X", "Fixes MX2-NNNNN"), or journey narration ("We considered X but went with Y", "Previously this was..."). That belongs in the PR description, ticket, commit message, or code search.
- Applies to line comments, block comments, JSDoc, and docstrings equally.

### Scope discipline (YAGNI)

- Don't add features, refactor, or introduce abstractions beyond what the task requires. A bug fix doesn't need surrounding cleanup; a one-shot operation doesn't need a helper.
- Don't design for hypothetical future requirements. Three similar lines is better than a premature abstraction. No half-finished implementations either.
- Don't add error handling, fallbacks, or validation for scenarios that can't happen. Validate only at system boundaries (user input, external APIs, deserialized payloads); inside the codebase types are the contract, so a defensive `if not x` on a type-narrowed parameter is dead code.
- Prefer editing existing files to creating new ones. Don't proliferate utility modules for one-off helpers. A new file is justified by a clear ownership boundary (a new domain, a new public interface), not by "this didn't fit anywhere obvious."
- Don't use feature flags or backwards-compatibility shims when you can change the code directly, and don't leave cleanup hacks behind: renamed unused `_vars`, re-exports from removed modules, `// removed` comments, `/* @deprecated TODO */` blocks that never resolve. If something is unused, delete it completely.

### Frontend completion criteria

- For UI or frontend changes (nextjs-app, the Word/Outlook add-ins, ai-doc-chat, and common-ts changes that surface in any consumer), start the dev server and verify the feature in a browser before claiming the task complete: golden path, edge cases, and regressions in adjacent features. Passing type checks and tests is not feature verification; if you cannot test the UI in a browser, say so explicitly rather than claiming success.

## Response Behavior

- **No destructive git operations.** Do not run `git reset`, `git checkout <branch>`, `git stash`, or `git rebase` unless explicitly asked; the user manages branch mutations in the main checkout. Force-push still needs the verb (below).
- **Push and open PRs without asking; open them with `/pr`.** A feature-branch push is a reversible two-way door and the PR gate protects `main` (project `.claude/rules/build-commands.md` Git Workflow), so no confirm is needed. Use the `/pr` skill, never raw `gh pr create`: it resolves the Jira ID from branch and commits, runs lint/type checks, and applies the repo template. Every PR carries a Jira ticket; if none exists `/jira` creates one, parented to an epic where one applies. Never invent a ticket number, never push to `main`, never bypass branch protection.
- **Destructive-op confirmation: name the verb.** When confirming a destructive op (force-push, deploy, delete, drop, merge), ask for a keyword naming the operation (`force-push`, `ship`, `merge`, `drop`), not generic `go`/`yes`/`ok` (fine for non-destructive confirms only).

The failure shape is an offer like "reply `approve` and I'll do both, or `approve` alone for just the first", where the identical token means two different things and the reply cannot disambiguate, so I pick the wider reading and mutate more than may have been intended. ## Reflection Trigger

When the user corrects your approach or a tool call fails:
1. Extract a 2-3 word topic and classify into a domain (`testing`, `style`, `architecture`, `security`, `debugging`, `verification`, `workflow`, `skill:<name>`, `agent:<name>`)
2. Search for prior corrections: `bd memories correction:<domain>`
3. If a match exists on the same topic and is <30 days old: invoke `/reflect` with the correction context and the prior memory
4. If no match: save the correction as `bd remember --key="correction:<domain>:<specific>" "<date>: <1-line summary>"` and continue working
5. **Stop tallying when reflection has converged.** If `/reflect` concluded "no edit needed" AND an umbrella memory (`correction:<domain>:<topic>`) plus structural enforcement (hook, linter, gate, formatter) both exist, do NOT save another dated recurrence entry. If the topic recurs past that, the next move is mechanical (a different enforcement layer), NOT procedural (more memories, more rule sharpening).

Do not rationalize skipping this: "too minor to reflect on" (you cannot judge significance without searching), "I'll remember next time" (you will not; compaction erases it), "the task is more urgent" (steps 1-2 take <1s), "I already adjusted my behavior" (in-conversation is not durable). The inverse, "log this slip for the record": step 5 governs.
