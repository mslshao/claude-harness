# 2026-06-03: A recurring style correction needs mechanical enforcement, and the mechanism climbs a ladder (own-loop)

**Source**: the author's own harness, evolved across several sessions and signed off on 2026-06-03. The artifact is the enforcement history of a single style rule (no em-dashes, the U+2014 character) and one falsified refactor along the way. Scrubbed for public version.

**Context.** The author has a hard personal style rule: never emit the em-dash character (U+2014) on any output surface. The rule started where every style preference starts: as a line in the prompt ("no em-dashes"). That is the cheapest possible enforcement, and it degrades in a specific way. The model honors the rule when it is deliberately scanning its own output for the character, and slips when it is generating freely (the character is a natural connector in trained English prose, so it surfaces exactly when attention is elsewhere). A prompt rule is a request the model satisfies on the turns it remembers to.

This is the general failure mode the entry names: a style correction that prompt-plus-memory cannot stop. Adding a memory ("remember, no em-dashes") does not change the mechanics; it is still a request the model honors when scanning and slips when generating. The recurrence is structural, not a matter of the model trying harder.

**What AI did.** The enforcement evolved up a ladder, each rung trading model-friction against the same guarantee. The rungs, in order:

- *Rung 0: the prompt rule.* "No em-dashes." Degrades as described above.

- *Rung 1: hooks that block-and-retry.* A PostToolUse hook (`block-em-dash.sh`) scans files after write; a Stop hook (`stop-validate-emdash.sh`) scans chat output. Both exit 2 to block and force a retry, which moves enforcement from "the model remembers" to "the harness checks every write deterministically". The Stop hook strips fenced code blocks before scanning (so a code sample that legitimately shows the character is not a false positive) and uses a `stop_hook_active` loop guard to cap retry cost so a stubborn turn cannot loop forever.

- *Rung 2: coverage extended to more surfaces.* The same rule was extended to Bash `gh`/`git` commit-message commands and to Jira and GitHub MCP write bodies and titles. The design decision here was "one rule, many surfaces": keep the logic inside `block-em-dash.sh` by grepping the opaque command string (which is what every existing Bash hook already does) rather than building a fragile heredoc/payload parser, and rather than splitting the rule across multiple hook files. A shared-lib extraction was deferred until a second concrete rule needs the same shape, not built speculatively.

- *Rung 3 (the key step, signed off 2026-06-03): silent auto-replace on prose surfaces.* `block-em-dash.sh` was converted from block-and-retry to a PreToolUse hook that emits an `updatedInput` rewriting the tool input (U+2014 to a hyphen) and returns allow. This applies to `.md` writes, Jira and GitHub MCP bodies, and commit-message commands (including referenced body-files, which are patched in place). The effect is that model friction on prose drops to zero: there is no retry, because the violation is silently corrected before the tool runs. The guarantee (no U+2014 reaches a prose surface) is identical to Rung 1; only the friction changed.

Two deliberate non-extensions of Rung 3:

- *Non-`.md` source and config writes (`.py`, `.ts`, `.tf`, `.json`, `.sh`) still hard-block at exit 2.* A literal U+2014 in source or config may be intentional (a string constant, a test fixture, a comment that quotes the character on purpose), so silent rewriting there would be wrong. Auto-replace is only safe where the character is never load-bearing, which is prose.

- *The Stop hook stays block-and-retry.* A Stop hook cannot rewrite chat text; it can only block and ask the model to regenerate. So chat output is the ceiling of the ladder: the surface where auto-replace is structurally impossible, and block-and-retry is the best available rung.

**The falsified refactor (honest subplot).** An auxiliary audit recommended making the Stop hook match a sibling hook's extraction logic: the sibling joins the full turn (all assistant blocks) before scanning, and the audit flagged the Stop hook's "last block only" scan as the weaker version, recommending parity. The recommendation was applied, then immediately falsified in practice. On a long tool-using turn, the full-turn join fired on a U+2014 sitting in an already-sent earlier assistant block. A Stop hook cannot fix already-sent text; only the final message is still in play. The result was an unsatisfiable block-retry that only the loop guard stopped. It was reverted to last-block-only. The lesson: a cross-hook parity recommendation needs a surface-purpose check first. The sibling hook joins the full turn because it detects a structured render that legitimately spans blocks; per-message prose hygiene only needs the one block that is about to end the turn. Same code shape, different surface purpose, and copying the shape broke the hook.

**Baseline.** The human-only alternative to each rung is self-discipline plus reviewer catch. Without Rung 1, the prompt rule slips on free-generation turns and the violation ships until someone notices it in a PR body, a Jira comment, or chat. Without Rung 3, every prose violation that Rung 1 catches still costs a retry round-trip (the model regenerates the whole tool call to remove one character). Auto-replace removes that round-trip entirely on the surfaces where it is safe. There is no wall-clock baseline to cite here; the cost the ladder removes is correction round-trips and shipped slips, not minutes.

**Verifiability.** The hooks are observable artifacts: `block-em-dash.sh` (PreToolUse, now auto-replace on prose, hard-block on source) and `stop-validate-emdash.sh` (Stop, block-and-retry, last-block-only). The decision is captured under a bd memory key (`decision:hook-emdash-autoreplace-2026-06-03`). The falsified refactor is verifiable as a revert: the Stop hook is last-block-only, not full-turn-join, and the reason is recorded. What is NOT independently verifiable by an external reader is the slip rate before versus after each rung; the author did not instrument a count, so the claim "the prompt rule degrades" rests on observed recurrence, not a measured rate.

**Honest read.**

1. *What this entry supports.* When a style correction recurs past prompt-plus-memory, the durable fix is mechanical enforcement, and the mechanism can climb a ladder that holds the same guarantee while reducing model friction: prompt rule, then block-and-retry hook, then silent auto-replace where the character is never load-bearing. It also supports a narrower, sharper claim: a cross-hook parity recommendation that looks like a clean refactor can be wrong, because two hooks with the same code shape can have different surface purposes, and the only way to catch that is a surface-purpose check before applying the parity move.

2. *What this entry does NOT support.* It does not support a measured reduction in slip rate; no before/after count was instrumented, so "the prompt rule degrades" is an observation, not a metric. It does not support that auto-replace is the right rung for every rule; it is only safe where the corrected token is never intentional, which is why source files stay hard-block and chat stays block-and-retry. It does not support that the ladder generalizes to corrections that are not mechanically detectable: this rule works because a single character is grep-able and its correct replacement is unambiguous, which is the easy case. A style rule that requires judgment (tone, structure, naming) has no auto-replace rung and may have no reliable hook rung at all.

## Caveats specific to this entry

- *Selection bias.* This is written up because the ladder converged and the falsified refactor was caught. A rule where mechanical enforcement failed, or where auto-replace silently corrupted intended text, would be the more instructive entry, and it is not this one.
- *Tooling generation.* The auto-replace rung depends on the PreToolUse `updatedInput` capability being available in this harness generation. On an earlier harness without input rewriting, Rung 3 would not exist and block-and-retry would be the ceiling for prose too. The ladder is shaped by what the tooling permits, not by a timeless principle.
- *Sample size.* N=1 rule. The ladder pattern is drawn from a single style correction whose defining property (a single, grep-able, unambiguously-replaceable character) is unusually friendly to mechanical enforcement. One rule climbing cleanly is not evidence that arbitrary corrections climb the same ladder.
- *Self-referential verification.* The author wrote the rule, the hooks, and this entry. The "guarantee preserved across rungs" claim is verified against the author's own hooks and bd memory, not by an independent party.

## The core pattern: escalate to mechanism, then minimize friction without losing the guarantee

A recurring correction that prompt-plus-memory cannot stop is a signal that the enforcement layer is wrong, not that the model needs reminding. The move is to climb: from a request the model honors when it remembers (prompt), to a deterministic check the harness runs on every write (block-and-retry), to a silent correction that removes friction entirely where the corrected token is never intentional (auto-replace). Each rung must hold the same guarantee; the only thing that changes is how much the model has to fight the rule. Where auto-replace is unsafe (source files, chat output) the ladder simply stops at the highest safe rung rather than forcing a friction-free path that would corrupt intended text.
