# 2026-06-11: A principle nested inside a conditional reads as a license (own-loop)

**Source**: the author's own session, 2026-06-11. A senior reviewer ran a planning/refinement session for an MX2 change through a different Claude model (Fable-class, a more literal rule-reader). The draft plan's sizing claim slipped past the verify-and-refine pass; catching that slip surfaced a structural flaw in a project rule. The fix landed as a small PR merged the same day. Scrubbed for public version.

**Context.** The MX2 rule corpus includes a "PR Size Discipline" rule in `code-style.md`. It carried two distinct ideas: an unconditional CONCERN test ("one PR maps to one concern") and a SIZE heuristic (a ~250-line trigger above which a PR should be split). The old prose NESTED the concern test inside the size conditional. A reader walking the rule top-down sees the size trigger first, then the concern test as a clause under it.

A model treats the rule corpus as an executable specification and reads it literally. Nesting the concern principle inside the size conditional invites the contrapositive: if the size trigger is what gates splitting, then "under the ~250-line trigger" reads as a license to bundle multiple concerns. The principle that was meant to be unconditional became, on a literal read, conditional on size.

**What AI did.** The failure surfaced live, then the fix was authored and verified:

1. *The live red.* The senior reviewer drove a plan-refinement session through a Fable-class model. The draft plan's Size/PR section asserted "one PR, under the ~250 trigger." The verify-and-refine pass checked the code claims in the plan but RUBBER-STAMPED the sizing claim, because the rule prose, read literally, licensed it. The real change spanned three concerns (a shared module, a library, and the consumers of both) that the reviewer would stack as three separate PRs. The single observed red was this one planning session.

2. *The fix.* The rule was restructured concern-first, size-second, shipped as a Jira ticket and a small PR approved by the senior reviewer and merged the same day. The new text states the concern principle UNCONDITIONALLY, outside the size scope, and marks the size number as a one-way trigger: over the threshold implies split; under the threshold does NOT imply bundle. The contrapositive license is removed because the principle no longer sits inside the conditional.

3. *Forward verification.* Clean-context replays (both a quiz harness and a plan-refinement harness) did NOT reproduce the live red against the OLD text. A fresh-context model, asked cold, did not make the misread on demand. But the NEW text's effect IS directly observable: a plan-refinement replay shows the model explicitly REJECTING "under the trigger" as a forbidden justification and re-grounding on concern-mapping. The fix is verified forward even though the original failure was not reproducible on demand.

**Baseline.** Without the harness's posture, the failure mode has a quieter shape. The rule corpus is the spec the agent executes against; an ambiguity in it is not a typo, it is a behavioral bug that ships silently. A human reader of the old rule applies intent ("of course the concern test still applies") and never notices the nesting. A literal model takes the contrapositive and treats the size threshold as the gate. The gap is invisible from the human side precisely because the human supplies the intent the prose omits. Left unfixed, every plan-refinement pass driven through a literal-reading model risks rubber-stamping a multi-concern PR as long as it sits under the line threshold.

**Verifiability.** The rule change is observable: the restructured "PR Size Discipline" section in `code-style.md`, the Jira ticket, and the small PR merged the same day. The forward-verification signal is observable in the plan-refinement replay transcript, where the new text causes the model to reject "under the trigger" as a justification and re-ground on concern-mapping. The one signal that is NOT observable on demand is the original red: clean-context replays against the old text did not reproduce it.

**Honest read.**

1. *What this entry supports.* A rule that nests a principle inside a conditional can be read by a literal model as licensing the contrapositive, and authoring the principle unconditionally (outside the conditional scope) with thresholds marked as one-way triggers removes that license. The forward effect of the fix is directly observable in replay: the model now rejects the under-threshold justification. The narrow claim is that the rewrite changed the model's reasoning on the sizing question in the replay, in the intended direction.

2. *What this entry does NOT support.* It does not support the claim that the old text reliably caused the misread. Clean-context replays (both harnesses) failed to reproduce the live red; the single observed red was one planning session driven by another person through a Fable-class model, and that exact condition was not reproduced on demand. So the causal link between the old nesting and the live failure is plausible but not demonstrated. It also does not support the idea that the rule fix closed the whole gap. Both replay runs concluded "1 PR on the merits" (a `flush()` helper alone is unreachable dead API, and the wiring is inert without instrumentation), while the reviewer's correction was 3 PRs split by layer. "Shared-module changes ship as their own stacked PR" is the reviewer's standard-in-use, but it exists nowhere in the written rules and needs team ratification. The rule fix removed the contrapositive license; it did not encode the unwritten stacking standard. That latent gap remains.

## Caveats specific to this entry

- *Selection bias.* This is written up because the rule flaw was caught and a fix shipped the same day. A nesting ambiguity that never produced a visible red would not have been noticed, and is not in this corpus.
- *Tooling-generation.* The live red was produced by a Fable-class model, a more literal rule-reader than the model that authored the fix. A different model generation reading the same old text might never have taken the contrapositive, which is consistent with the clean-context replays failing to reproduce it. The failure mode is partly a property of which model reads the spec, not of the spec alone.
- *Sample-size.* N=1 live red, not reproducible on demand. This case supports "the rewrite changed the model's reasoning in replay"; it does not support a frequency claim about how often literal models take the contrapositive on nested principles.

## The core pattern: rules are executable specs, so author principles unconditionally

A model reads the rule corpus as a specification and follows it literally. Intent that a human supplies for free does not transfer; only the structure on the page does. When a principle is nested inside a conditional, the contrapositive is available, and a literal reader will sometimes take it. The harness fix is structural: author principles UNCONDITIONALLY, outside any conditional scope, and mark thresholds as one-way triggers (over implies split; under does not imply its opposite). The threshold then constrains in one direction only and cannot be read backward as a license.

## Why this entry matters for the repo

Most of `evidence/` is shaped around AI doing a thing faster than a human would. This entry is about the harness's own surface as the failure point: the rules that drive the agent are themselves a program, and a program with an ambiguous branch has a bug. The honest core here is the asymmetry between the two verification signals. The fix is verified forward (the new text demonstrably changes the model's reasoning in replay), but the original failure was not reproducible on demand, so the claim is bounded to "the rewrite moved the model in the intended direction" rather than "the old text reliably caused the failure." Naming that boundary, plus the still-unratified stacking standard left in the open, is the discipline this entry is for.
